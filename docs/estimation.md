# 週制限の実効容量推定: 方法と限界

推定結果は「現在のモデル構成・使い方における推定」であり、プランの公式上限ではない。

## 4種類の数値

| 種類 | 置き場所 | 画面での表し方 |
| --- | --- | --- |
| ログ使用量 | `usage_events` | 単位「トークン」 |
| API料金換算 | `usage_events.cost_nano`（取り込み時に計算） | 「$〜 相当」「API料金換算（請求額ではありません）」 |
| 公式利用率 | `quota_observations` | 「%」と取得経路・取得時刻（古い値は「古い値」） |
| 推定 | 計算結果（`EstimateView`） | 「推定」の札、値は幅で表示 |

## 基本式

同じ枠・同じ周期の2つの観測 p1 → p2（Δp ＝ p2 − p1 ポイント）の間の端末上の使用量を T（トークン）、C（API料金換算）とすると、

- 参考の枠全体トークン量 ＝ T × 100 / Δp
- 参考の枠全体換算額 ＝ C × 100 / Δp

公表値が整数に丸められている場合、真の増分は (Δp − 1, Δp + 1) にあるため、区間ごとに幅 [T×100/(Δp+1), T×100/(Δp−1)] を出す。

## 区間の作り方（`src/core/estimate/estimator.ts`）

1. 直近8週間の観測を使う（使い方の変化を反映するため）。周期（同じリセット日時）ごとに観測を時刻順に並べる。利用率が欠けた観測は使わない。
2. Δp が最小幅（既定 5 ポイント）に達するまで区間を伸ばす。
3. 区間ごとに除外・注意の理由を記録する。

| 理由 | 扱い |
| --- | --- |
| リセットをまたぐ | 除外 |
| プランが変わった | 除外 |
| 利用率が減った | 除外 |
| 100% に張り付き | 除外 |
| 推定周期（観測の無い周期） | 除外 |
| API 利用・追加課金が混在 | 除外 |
| 端末上の利用が無い（別端末・Web 等） | 除外し、推定の抑制を判断 |
| 他の区間より容量が極端に小さい（中央値の半分未満、区間が3つ以上のとき） | 「未観測の利用の疑い」として除外。黙って消さず画面に表示 |
| 短い区間（10分未満）、未換算が多い（20% 超）、丸め誤差が大きい | 注意として表示 |

4. 除外されなかった区間を、Δp を重みにした重み付き中央値でまとめる。幅は四分位と丸め幅の中央値を合わせて出す。
5. 状態:
   - 推定あり: 採用区間が2つ以上
   - 推定準備中: 採用区間が1つ（条件付きの参考値を表示）、または変化がまだ小さい
   - 推定困難: 未観測の利用の疑いが区間の 30% を超える、または使える区間が無い
6. 未換算のトークンが採用区間の 20% を超える場合は、金額の推定を控える（トークンの推定は出す）。

## 残量とペース（`src/core/estimate/pace.ts`）

- 公式の残り: 最後の観測の値。取得から30分を超えたら「古い値」。
- リセット予定時刻を過ぎて新しい観測が無い場合は「リセット予定時刻を過ぎました（新しい公式値は未取得）」とし、0% とはみなさない。
- 補助推定: 最後の公式観測以降のローカル使用量を推定容量で割ったもの。公式値とは別の項目で表示する。
- ペース: 直近24時間（同じ周期内）の観測から求め、丸めの幅を含めて枯渇予測時刻を幅で出す。

## 利用枠の計画（ダッシュボード・消費率・シミュレーター）

計算は `src/core/plan/`、DB からの材料集めは `src/query/plan.ts`。公式観測値・ローカルログからの値・推定を別の項目で返し、画面では「公式」「計画」「推定」の札で区別する。

### モデル×エフォート別の消費率（`rates.ts`）

1. 公式利用率が切り替わった時点（変化点）どうしを区間にする。表示が整数でも、変化点から変化点までの真の増分はほぼ Δp に等しい（ずれは取得時刻の粗さだけ）。リセット・プラン変更・減少の所で区切る。
2. 区間内のローカル使用量を「モデル|エフォート」別に集計し、1つの組み合わせがトークンと出力の両方で 85% 以上を占める区間だけを、その組み合わせの観測にする。複数を混ぜた区間からは係数を分けられないため使わない（全体平均には入れる）。
3. 同じ組み合わせが続く区間を、変化が 3 ポイント以上になるまでまとめ、ΣΔp ÷ Σトークン（100万トークンあたり）、ΣΔp ÷ Σターン（1回あたり）、ΣΔp ÷ Σセッションを出す。幅は区間の選び直し（10〜90%）。
4. 「実測」は区間 3 つ以上かつ合計 10 ポイント以上。足りなければ「暫定」。区間が無い組み合わせは値を出さない。
5. 入力（キャッシュ書き込みを含む）・キャッシュ読み取り・出力の係数は、区間が 12 以上あり、3つの量が互いに独立に動いている（相関 0.95 以下、ばらつきあり）ときだけ、非負の最小二乗で求める。そうでなければ「不明（分けられない）」と表示する。実データでは比率がほぼ一定のことが多く、多くの組み合わせで「不明」になる。
6. API 料金は使わない（サブスクの消費は非公開の係数で決まり、API 単価に比例する保証が無いため）。
7. ログに使用量が無いのに利用率が増えた区間は「別端末・Web などの疑い」として数え、推定には使わない。

アカウント情報が記録される前（アカウント不明）の観測は、そのプロバイダーの既知のアカウントが1つだけの場合に限り、同じ利用者のものとして含める。

### 予測（`forecast.ts` の `forecastWindow`）

過去の完了した周期（同じプラン、新しい方から使えるものを最大 8 個）それぞれについて「今と同じ経過時点から周期の終わりまでに何ポイント使ったか」を求め、今の値に足したものを将来の候補にする。曜日・時間帯の癖は過去の周期に含まれる。

次の周期は使わない（理由は画面の計算結果 `reasons` に残す）:

- 記録が途中で終わった周期（最後の観測が周期の 85% より前で、100% にも達していない。早めのリセットなど）。周期の終わりの値が分からないため。
- 今と同じ経過時点ですでに 100% だった周期。その後の消費が上限で打ち切られていて比べられないため。

実ログでは、これらを「その後の消費 0」として数えた最初の版で、毎週上限に達している利用者に対して「リセットまで持つ」と誤って予測した（2026-11-18 に修正）。

- リセット時の見込み: 候補の中央値と 20〜80% の幅。
- 枯渇の見込み時刻: 中央の候補で上限に達する時刻（達しなければ出さない）。早い場合は 20% 点。
- 持つ確率: 過去の周期が 4 つ以上あるときだけ、上限に達しなかった候補の割合を出す。少なければ確率を出さない。
- 直近ペース: 直近 24 時間の公式値の増え方が休まず続いた場合の枯渇時刻。別の項目として表示する。

### 1日ごとの予算（`budgetPlan`）

今日の始まりの公式値から「目標残量」を引いた残りを、リセットまでの各日に曜日の重みで割り振る。今日の予算と今日の使用（今の公式値 − 今日の始まりの公式値）を比べ、超えたら「超過」とし、明日以降の予算をその分減らす。曜日の重みは過去の消費（変化区間の Δp）を曜日別に平均して作る（最低 0.25）。設定で手動にもできる。

### 作業可能量とシミュレーター

- あと何回: 使える残り（目標残量を引いた後）÷ 1回あたりの消費。消費の幅から回数の幅を出す。
- 普段のペースで何時間: 期間の ΣΔp ÷ ローカル使用があった時間数で「作業1時間あたりの消費」を出し、残りを割る。
- シミュレーター: 選んだ組み合わせの 1回あたりの消費で、作業日・作業時間帯に均等に依頼する場合の推移を 1時間ごとに描く。消費率を求めた枠（週枠）だけで計算する。
- 「直近7日を別の組み合わせで処理していたら」: 同じトークン量 × その組み合わせの 100万トークンあたり消費。モデルが違えば必要なトークン数も変わるため条件付きの試算。

### 未実装

予測時点の値の保存と事後の比較（予測精度の継続評価）、通知、プランの比較、5時間枠の消費率（このPC の Codex には 5時間枠の記録が無い）。

## 限界

- Claude の公式利用率はログに無い。ステータスライン連携（デスクトップ版で動くかは未確認）か手動記録が必要。
- 別の端末・Web・モバイルでの利用は端末上のログに現れない。利用率だけが増えるため、上の除外規則で検出を試みるが、常に見分けられるわけではない。
- 利用率の反映の遅れは計測していない。区間を長め（既定 5 ポイント以上）にして影響を小さくしている。
- Codex の公表値は整数のため、Δp が小さい区間の誤差は大きい。
- 公式利用率の観測は、同じ値が続く間は15分ごとに1件だけ保存している（値の変わった時刻は残る）。区間の端の時刻は最大15分ずれる可能性がある。
- 区間の使用量は、取り込み時に保存した API料金換算を使う。
- モデル別の係数は推定していない（観測が足りないため。架空の倍率は置いていない）。モデル構成は推定画面に表示する。
- サブエージェントのログで出力が過小な期間（2026年10月の Claude）は、その期間の推定容量を小さく見積もる方向に働く。
