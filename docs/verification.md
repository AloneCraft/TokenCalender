初回の取り込みが遅かった原因（2026-11-18 に修正）:

- 公式利用率の重複確認の問い合わせが `COALESCE(window_minutes, -1) = ...` の形で、索引の「枠の長さ・時刻」の列を使えず、観測が増えるほど1件ごとの確認が遅くなっていた（200回の確認で 91ms → 修正後 1ms）。古い Codex ログには公式利用率の行が数百万あり、修正前は全取り込みが 20 分を超えた。`IS` で比べる形に直した。
- 改行の検索を1バイトずつの比較から組み込みの検索（`indexOf`）に変え、使わない行は文字に変換しないようにした（直近 400 ファイルで Claude 4.8 → 2.4〜2.9 秒、Codex 7.3 → 4.2 秒。新旧の経路の出力は一致）。
| 公式利用率の観測 | 約 54 万件 → 間引き後 約 2.5 万件（値の変わった時刻は保持） |

経緯（失敗から学んだこと）:

1. 版1: `token_count` の累積が減るたびにリセット扱いにして数え直し、合計が約38倍（3.65兆）に過大だった。
2. 版2: 2種類の累積の大きい方を到達点にしたが、1ファイル内で2列が交互に書かれる場合に約5倍の過大が残った。

4. 版4: 分類不明のトークンを残し、列が1つのときは欠けた行の分も数える。上の表の結果。M 型の 3 ファイルでは、2列目の始まりが1列目と一致しない場合に欠けた行と区別できず、わずかに多く数える。

### 分析ページの問い合わせ時間（実データ 64.2 万イベント、直近60日）

改善前は 60日分の約45万イベントを1件ずつ JS の部品に変えており、図によって 2.8〜8.9 秒かかっていた（読み込みだけで約3.5秒）。SQL 側で「5分 × 属性の組」ごとに合計してから読む経路（`loadEventAggregates`）にし、0.6〜0.8 秒になった。5分は最小の刻みで、暦の日・週・時の区切りは必ずその倍数に当たるため、結果は変わらない（10日分と60日分の実データで、従来の経路との差が 0 であることを確認。単体試験 `query.test.ts` でも全図・全切り口を比較）。セッション単位の図、金額の再計算が要る場合、期間の端が5分の区切りに合わない場合は、従来の1件ずつ読む経路を使う。時系列・カレンダーなど他の画面は対象外。
